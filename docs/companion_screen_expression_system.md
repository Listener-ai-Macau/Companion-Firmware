# Companion Screen Expression System

This document is the working acceptance map for the Companion screen expression
system. The first target is the WB55 devboard, but the model must stay portable
for a later WBA55 or WBA65 port.

## Development Rules

- Keep expression state and rendering input models under `app/companion_pendant`
  free of STM32 HAL, STMWPAN, Cube, board pin, and interrupt details.
- Use platform adapters for display transport. WB55 code may own SPI/GPIO/BUSY
  timing; a future WBA adapter must be able to reuse the same expression states.
- Keep `panel_adapter.h/.c` as a portable dispatcher. Real display transport
  must enter through the `comp_epaper_panel_refresh_fn_t` target-owned refresh
  callback, not by adding board IO to the portable screen files.
- Treat golden PBM fixtures as the no-hardware visual contract. If a rendering
  change updates fixture hashes, explain the product reason and rerun validation.
- Treat the physical product housing as the stable cat-head shell. The panel
  draws only internal expressive features: eyes, a compact nose/mouth rig,
  motion cues, and small status badges. It must not duplicate ears, a head
  outline, or whiskers.
- Keep feature proportions and anchors stable across states so the expressions
  remain one recognizable character instead of unrelated abstract faces.
- Keep idle visually quiet after its initial composed pose. CEMP may provide
  event timing, but an idle device must not spend refresh cycles repeatedly
  blinking or replaying fixed bitmap frames.
- BLE callbacks may request expression/card updates, but they should enqueue
  display work instead of blocking on panel IO.
- WB55 startup must request the default idle face through the same ExpressionV1
  queue path used by runtime events.
- Recording, speaking, error, sync, and low-battery expressions must remain
  visible product states. Do not hide a real capture, failure, or power warning
  behind a generic idle face.
- Transient acknowledgement faces may return to idle through a portable elapsed
  time tick, but recording, low-battery, and error faces must not disappear
  just because time passed.
- SettingsV1 quiet-hours and display-off hints may lower only idle to sleepy.
  They must not hide recording, low-battery, error, or other active product
  expressions, and WBA ports must preserve that stable-state guard.
- Real panel enablement must fill the panel hardware evidence template before
  any WB55 or WBA target claims a real refresh. The required evidence includes
  controller identity, target pins, BUSY/reset timing, host logs, visual
  before/during/after proof, and the target adapter file.

## ExpressionV1 States

ExpressionV1 covers:

- `idle`
- `listening`
- `thinking`
- `speaking`
- `happy`
- `sleepy`
- `recording`
- `sync_complete`
- `low_battery`
- `error`

The renderer currently supports 2.13 inch landscape and 1.54 inch square
monochrome e-paper targets.

1. No-hardware expression renderer
   - `expression` card type exists.
   - Every ExpressionV1 state renders deterministic PBM output for both display
     variants.
   - Human-readable preview: `docs/validation/epaper/expression-preview.svg`
     generated by `python .\tools\render_expression_preview.py --write`.
   - Paired acceptance id: `expression_visual_contract`.
     Title: Expression visual contract.
     The visual contract records ink density and pairwise face-crop distance
     for every ExpressionV1 PBM and rejects visually duplicate faces.
   - Paired acceptance id: `expression_visual_acceptance_matrix`.
     Title: Expression visual acceptance matrix.
     The matrix records every face/variant PBM path, hash, density result,
     source signals, policy cases, and host coverage in one row per face.
   - Paired acceptance id: `expression_layout_contract`.
     Title: Expression layout contract.
     The layout contract records title/body/footer text budgets for every
     ExpressionV1 state and rejects truncation or body/footer overlap.
   - Validation: `python .\tools\render_epaper_fixtures.py --self-test` and
     `python .\tools\verify_epaper_assets.py`; visual QA is covered by
     `python .\tools\verify_expression_visual_contract.py`,
     matrix coverage is covered by
     `python .\tools\render_expression_visual_acceptance_matrix.py`, and copy
     layout is covered by `python .\tools\verify_expression_layout_contract.py`.

2. BLE-to-expression policy
   - Map BLE/status snapshot inputs and diagnostic event names to listening,
     thinking, speaking, recording, sync-complete, low-battery, and error.
   - Keep the existing `CardWriteV1` contract compatible.
   - Validation: `python .\tools\verify_expression_policy.py` plus the existing
     static GATT contract check.
   - Current fixture: `docs/validation/companion-screen-expression-policy.json`.

3. WB55 display queue boundary
   - Add a firmware queue API that accepts expression/card updates without doing
     panel IO inside BLE callbacks.
   - Current implementation: `display_queue.h/.c` stores bounded CardWrite
     payloads and ExpressionV1 requests; WB55 `app_ble.c` enqueues from
     `CardWriteV1` and `Companion_Display_Task` publishes rendered status.
   - Validation: `python .\tools\verify_display_queue_static.py`, the WB55
     bring-up build, and diagnostic log events for render request/update result.

4. Display queue fault paths
   - Acceptance id: `display_queue_fault_paths`.
   - Queue full, payload-too-long, bad-argument, and unsupported-expression
     cases map to stable CardStatusV1 `last_error` values.
   - CardWrite queue-full failures publish `busy/queue_full`; payload-too-long
     failures publish `failed/payload_too_long`.
   - Expression enqueue failures publish host-visible status and roll back the
     portable expression state to the previous visible face.
   - Product invariant covered now:
     `expression_state_rolls_back_on_enqueue_failure`.
   - Evidence lives in
     `docs/validation/companion-screen-display-queue-faults.json`.
   - Validation: `python .\tools\verify_display_queue_fault_paths.py`,
     `python .\tools\verify_display_queue_static.py`, and the WB55 bring-up
     build.

5. Display queue telemetry
   - Acceptance id: `display_queue_telemetry`.
   - The portable queue tracks `pending_count`, `high-water` count,
     `dropped_count`, queue depth, payload bound, and monotonic in-memory
     sequence without adding any STM32/WB/WBA dependency.
   - `comp_epaper_display_queue_snapshot()` exposes those fields as a portable
     stats snapshot so WB55 and future WBA schedulers can log queue pressure
     without reaching into queue internals.
   - `high-water` records the largest pending queue depth since init and does
     not decrease when display work is dequeued. It helps diagnose slow
     e-paper refresh pressure on WB55 and future WBA targets without changing
     CardStatusV1.
   - WB55 diagnostics keep their current meaning:
     `e_paper.render_request` arg2 is the stats snapshot pending count, and
     `e_paper.update_result` arg2 is the stats snapshot dropped count.
   - Current fixture:
     `docs/validation/companion-screen-display-queue-telemetry.json`.
   - Validation: `python .\tools\verify_display_queue_telemetry.py`,
     `python .\tools\verify_display_queue_static.py`,
     `python .\tools\verify_display_queue_fault_paths.py`, and the WB55
     bring-up build.

     parameter-driven. It stores no panel-sized facial bitmap and keeps the
     same future WBA adapter boundary.

64. Revision 29 living emotional system
   - The face now has three deliberately separate timescales: an immediate
     event response, a bounded mood (`calm`, `curious`, `affectionate`,
     `delighted`, `restful`, or `worried`), and a compact memory record for
     attachment and accumulated interaction history. The mood is derived from
     valence, arousal, curiosity, affection, attachment, quiet time, and a
     deterministic sociability/sensitivity/playfulness personality seed.
   - Product events and touch advance the elapsed emotional state before they
     compose the next pose. This means a long quiet interval settles the pet
     without a periodic screen animation, while contact and meaningful product
     events create an immediate but non-random response. Recording/listening
     feeds curiosity, completion feeds warmth, and low-power/error states make
     concern visible without pretending they are positive interactions.
   - `comp_pet_behavior_memory_t` is intentionally target-owned persistence
     data. A target may coalesce CRC-protected writes into external user-data
     storage, but the portable behavior layer neither knows nor writes a Flash
     address. This prevents a future WBA adapter from inheriting WB55 layout
     facts or unsafe high-frequency wear.
   - The embedded self-test executes every named mood classification and the
     memory export/import round trip. Its compact boot log is engineering
     evidence only: it does not enqueue a panel refresh or stand in for the
     separately pending visual acceptance.
   - The product direction follows the useful system lesson, not the artwork,
     from CASIO's description of interaction-shaped emotional development and
     individual personality ([Moflin](https://www.casio.com/us/moflin/)), the
     distinction between immediate emotions, mood, and long-term attitudes in
     affective-robotics research ([Affective social robots](https://doi.org/10.1016/j.robot.2009.09.015)),
     and LOVOT's coordinated attention cues ([LOVOT technology](https://lovot.life/en/technology/)).

65. Revision 30 touch-safe panel wait buffering
   - FT6336 samples collected while the SSD1681 is busy retain only the first
     contact anchor, the newest held coordinate, and the release. No-contact
     polling samples are not queued. This keeps the portable gesture state's
     initial finger anchor and final position intact without allowing one slow
     e-paper refresh to fill a finite board-side queue.
   - The target-only coalescing lives in WB55 `main.c`; portable touch parsing,
     gesture semantics, emotion behavior, and the WBA callback boundary remain
     unchanged. The latest WB55 startup capture records about 300 touch polls
     with `buffered=0 dropped=0`; actual held-finger perception remains a
     separately pending human acceptance.

66. Revision 31 directional pet strokes
   - A point tap and a finger stroke now carry separate social meaning. A tap
     keeps precise eye contact. Every non-navigation left/right/up/down swipe
     on the daily face becomes a portable `pet_behavior` stroke: side strokes
     make a playful asymmetric side glance, an upward stroke makes a curious
     lifted-brow look, and a downward stroke settles into a warm smile with
     cheeks. The CEMP attention clip supplies the bounded three-phase timing,
     while the pose is still composed from exact logical end coordinates rather
     than a new bitmap set.
   - The old right-edge left-swipe drawer entry has been retired. In the current
     product rule, all ordinary left/right/up/down swipes feed direction,
     travel-derived energy, duration, affection, and arousal into the portable
     behavior model; only the completed anywhere, nearly-still 3 s long press
     can preempt a pet response and enter the menu. A slow downward stroke is
     more soothing; a quick upward or side stroke is more curious/playful. The
     next ordinary idle transition clears this transient stroke cue and performs
     the existing one quiet maintenance pass only.
   - This applies a transferable mature-companion rule without copying another
     product's art: interaction mode changes both immediate expression and
     short-lived affect, while attachment accumulates over time. CASIO describes
     Moflin's petting and interaction as shaping evolving emotion and
     personality ([Moflin](https://www.casio.com/us/moflin/)); LOVOT continues
     to emphasize coordinated eye contact and natural blinking
     ([LOVOT technology](https://blog.lovot.life/blog/search/?tag=technology)).
     The behavior and pose APIs remain MCU/panel/storage-free for WBA55/WBA65.
   - Four separate NUCLEO-WB55RG + SSD1681 machine probes now exercise one
     physical left, right, up, or down stroke per firmware image. The logs
     prove the expected asymmetric side glances, up-look spark, and warm
     downward smile reach the real panel through exactly one boot baseline and
   three interaction differential refreshes. This guards the end-to-end
   routing and expression parameters; it is intentionally not a claim about
   the human-perceived charm, touch feel, or residual quality, which remain
   in the explicit acceptance session.

67. Revision 35 product menu and deliberate hold
   - The menu is now organized around real Companion tasks: `record`, `status`,
     `phone`, `device`, `preferences`, and `about`. It deliberately does not
     expose an emote-preview sandbox, fake sync command, OTA control, or a
     storage control before those product workflows are accepted.
   - Daily face interaction stays social. A nearly still hold emits a single
     `hold` tease at 650 ms; only an anywhere `long_press` at 3000 ms enters
     the menu. All normal left/right/up/down swipes remain directional pet
     strokes, while left-edge right swipe remains the exit/back gesture.
   - The owner-accepted menu-v3 source keeps all six product destinations in
     one external 200x200 home frame per language. Its rows are tapped in
     place; it does not use a numbered scroll asset or item snapping. A row
     tap uses a press-cue partial refresh followed by a target-page arrival
     partial refresh. Neither cue is allowed to promote itself to a full
     refresh; `0xFC` remains the interactive waveform and `0xCF` remains the
     quiet maintenance waveform.
   - Touch and stroke animation use three sparse full-face poses: anticipation,
     peak reaction, and warm recovery. This applies the layered motion
   principle behind mature OLED pets without claiming a frame rate that a
   GDEY0154D67/SSD1681 e-paper panel cannot deliver. The pose/behavior
   contract remains target-free for STM32WBA55/WBA65 reuse.

68. Revision 35 premium pet polish
   - The current product subgoal is premium companion feel: the device should
     read as one living character with memory and nonverbal reaction, not as a
     catalog of unrelated face templates. Current reference principles are
     broad expression sets, touch/gesture input, personality over time, and
     coordinated whole-face/body-language cues; the firmware must not copy
     another product's artwork or assume OLED refresh rates.
   - The normal product art path now uses external CEMP PBM frames generated
     from `card_renderer.py` and the `genref_sheet_12_inner_faces_v5` style
     contract. Each expression frame changes the whole inner face together:
     brows, bean eyes, highlights, eyelids, nose/mouth, cheek marks, and small
     state symbols are treated as one rig. The compact procedural path remains
     available only for rescue, maintenance, and small WBA-reusable behavior
     fallbacks; it must not replace the external art pack for normal product
     expressions.
   - The product menu follows the owner-accepted `menu-v3-2026-07-13` sheet.
     Its source image is cropped into seven complete Chinese and English pages
     in external CEMP revision 53: home, Voice & Record, Status, Phone Link,
     Device, Preferences, and About. The compact line art, black selection,
     and page composition come from that source image, not a hand-drawn MCU

     datum cells. The physical shell owns the cat outline, so firmware must

     The premium pet art contract is guarded by

   - Generated art enters firmware through the named
     `genref_sheet_12_inner_faces_v5` expression contract and the
     `MENU_V3_STYLE` source-image import contract. `card_renderer.py` owns

     the approved menu source hash and crop map. A new generated reference is
   implemented by revising its versioned prompt/reference, regenerating
   external assets, and rerunning the verifiers, not by scattering one-off
   coordinates through runtime render code.

69. Queued interaction-state art baseline
   - Before any new expression implementation, SCR-21 must retain priority:
     the connected `TP_INT -> PC6` path needs real IRQ and Stop-resume
     evidence. This item deliberately adds no new screen traffic or wake
     timer while that work is in progress.
   - The next generated-art sheet has seven semantic states: `low_power_idle`,
     `touch_wake`, `tap_ack`, `directional_swipe`, `recording_start`,
     `recording_active`, and `recording_saved_or_failed`. It must use the
     accepted `generated_pet_expression_sheet_v5.png` inner-face language as
     its baseline: pure black on white, no cat-head outline, ears, body, or
     device frame. Eyes, brows, lids, mouth/nose, cheeks, and sparse state
     marks must change together rather than turning the state into an eye-only
     swap.
   - `low_power_idle` is a persistent sleeping pose, not an animation loop.
     It is the last stable frame before Stop and must not schedule periodic
     refreshes. A TP_INT first wakes the MCU; after the decoded touch is known,
     `touch_wake`, `tap_ack`, or `directional_swipe` may issue one coalesced
     interaction partial refresh. This preserves the low-power contract and
     avoids a speculative flash merely because an interrupt arrived.
   - The existing daily double tap remains the recording command. Its visible
     journey will be `recording_start` -> `recording_active` ->
     `recording_saved_or_failed`, driven only by real recording FSM state and
     external-Flash completion result. Recording and saving states block Stop;
     a completed successful journey may later settle to the static low-power
     pose. No wake-word art is introduced here because wake-word capture is
     explicitly deferred by SCR-18.
   - Art generation, review, prompt text, source hashes, image-to-PBM review,
     CEMP revision, and hardware acceptance must be recorded in
     `docs/art/iterations/companion-pet-interaction-v1/iteration-ledger.json`.
     Until an output is accepted, current external assets remain unchanged.

70. Revision 72 interaction refresh cadence (supersedes earlier generic quiet
    maintenance wording)
   - Normal daily tap, stroke, menu drag, ordinary menu navigation, recording
     status update, and phone reconnect use the portable
     `PARTIAL_INTERACTIVE` intent only. They must not schedule an application
     timer that issues a second cleanup waveform after the user's finger has
     stopped.
   - `refresh_policy.h/.c` counts successful differential requests after a
     valid baseline. Requests 1-5 remain differential (`0xFC` on this WB55
     target); request 6 selects one target fast maintenance waveform (`0xC7`
     with the recorded Good Display Mode-1 profile) and resets the count.
     This is the active ghost-control cadence for WB55 and future WBA targets.
   - Explicit menu entry and right-swipe exit are readable visual boundaries,
     so each may request one `MAINTENANCE` cleanup. Standard full refresh
     (`0xF7`) remains initial-baseline and fault-recovery only. Earlier text
     mentioning a 1200/1600 ms generic quiet cleanup, `0xCF` for normal
     interaction, or a 60-update interactive safety limit is historical and
     must not be reintroduced.
   - This removes a software-added second wait but does not claim OLED frame
     latency. The actual panel still needs focused residual-image and feel
     review under ACPT-01 after a reset-bounded WB55 trace proves the cadence.
